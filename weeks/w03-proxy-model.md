## 为什么学这个

「翻墙」这个词很模糊。技术上说，它做的是**代理**：让你的流量先到一个你能连上的地方，再由那里替你访问目标。

这一周你要亲手写一个 SOCKS5 服务器（不到 40 行），因为**写完它，你就再也不会觉得代理是魔法**。

## 核心概念

### 1. 正向代理 vs 反向代理

| | 正向代理 | 反向代理 |
|:--|:--|:--|
| 谁配置它 | 客户端 | 服务端 |
| 代表谁 | 代表**客户端**去访问外部 | 代表**服务器**接受外部访问 |
| 例子 | 浏览器代理、SS/V2Ray 本地端 | Nginx、CDN |
| 你关心的 | ✅ 这个 | 顺带了解 |

抗审查用的是**正向代理**：客户端主动把流量交给它。

### 2. 两种隧道协议

**HTTP CONNECT**（最古老，最好懂）：

```
客户端 → 代理:  CONNECT www.example.com:443 HTTP/1.1
代理   → 客户端: HTTP/1.1 200 Connection Established
（之后这条 TCP 连接就变成透明管道，双方直接收发字节）
```

**SOCKS5**（RFC 1928，更通用）：分两步。

**第一步 · 方法协商**

```
客户端 → 05 01 00           # VER=5, NMETHODS=1, METHODS=[0x00 无认证]
服务端 → 05 00              # VER=5, METHOD=0x00
```

**第二步 · 请求**

```
客户端 → 05 01 00 03 0b "example.com" 01bb
         │  │  │  │  └─ 域名长度 11 └─ 端口 443
         │  │  │  └─ ATYP=3 (域名)  └─ 域名
         │  │  └─ RSV
         │  └─ CMD=1 (CONNECT)
         └─ VER
服务端 → 05 00 00 01 00 00 00 00 00 00   # 成功
```

`ATYP`：`1`=IPv4，`3`=域名，`4`=IPv6。**注意 `3` 的存在**——它允许客户端把**域名**而不是 IP 交给代理，由代理去解析。这一点直接决定了 DNS 会不会泄漏。

### 3. DNS 泄漏的根源

| 用法 | 谁解析域名 | DNS 查询走向 | 是否泄漏 |
|:--|:--|:--|:--|
| `curl --socks5 127.0.0.1:1080` | **本地**先解析成 IP，再交给代理 | 走你本机的 DNS | ❌ 泄漏 |
| `curl --socks5-hostname 127.0.0.1:1080` | 代理端解析（ATYP=3） | 走代理的 DNS | ✅ 不泄漏 |

这就是为什么所有严肃的代理配置里，**必须**让域名走代理去解析。

### 4. 透明代理 / TPROXY

不是所有程序都支持设代理（比如某些游戏、某些系统更新）。透明代理用 `iptables` 的 `REDIRECT`/`TPROXY` 在**网络层**把流量劫走，程序自己毫无感知。

代价：需要 root、需要处理 DNS、容易和 IPv6 打架。W10 之后你会用到。

## 实验：你写的代理，它到底看见了什么

跑起来之后，问自己三个问题：

1. **代理能看见你访问的域名吗？** 能（ATYP=3 时它收到的就是域名）。
2. **代理能看见你的 HTTP 内容吗？** 不能——因为在它之前 TLS 已经加密了。它只是转发密文。
3. **代理能看见你访问的 IP 吗？** 能，而且必须能，否则它没法转发。

> 关键认知：**代理不是「解密再转发」，而是「转发加密后的字节」**。所以 TLS 是端到端的：`浏览器 ⇄ 目标网站`，代理夹在中间只是搬运工。
>
> 推论：任何声称「中间人能看到你 HTTPS 内容」的方案，都必须让你安装一张根证书。这就是企业监控的原理，也是为什么「证书告警」不要随手忽略。
