## 为什么学这个

到这一步，你已经能凭感觉说「今天有点卡」。但**感觉不能优化，也不能证明**。

这一周把「卡不卡」变成一张表、一条曲线、一个可以复现的结论。这是从「玩家」到「工程师」的分界线。

## 核心概念

### 1. 指标定义

| 指标 | 定义 | 为什么重要 |
|:--|:--|:--|
| **RTT** | 往返时延（ping） | 交互体验的基础 |
| **抖动（jitter）** | RTT 的方差 | 视频/语音的杀手 |
| **丢包率** | 丢失包 / 总包 | 直接决定 TCP 吞吐 |
| **吞吐** | 单位时间传输量 | 你能不能看 4K |
| **TTFB** | 首字节时间 | 页面「感觉快不快」的关键 |
| **可用性** | 成功请求 / 总请求 | 稳定性 |
| **风控评分** | 平台/第三方对这个 IP 的信任度 | 能不能「用」而不只是「通」 |

### 2. 为什么单次测速没有意义

三个原因：

1. **时间维度**：晚高峰（20:00–23:00）和平峰差 5–10 倍是常态
2. **统计维度**：单次测量无法区分「偶发丢包」和「持续劣化」
3. **路径维度**：RTT 只说明总时延，不说明瓶颈在哪一跳

**正确做法**：固定时间点、连续采样、看分布而不是看均值。

### 3. 该看 P50 还是 P95

- **P50（中位数）**：典型体验
- **P95**：差的时候有多差
- **P99**：极端情况

**对代理来说，P95 比 P50 重要得多**——因为你能忍受「平均 200ms」，不能忍受「每 20 次就有 1 次卡 3 秒」。

### 4. 采样设计

一个能得出可靠结论的最小方案：

| 项 | 建议 |
|:--|:--|
| 采样点 | 每天 4 次：10:00 / 15:00 / 21:00 / 23:30 |
| 每次样本 | ping 100 个包、mtr 50 个包、curl 5 次取中位 |
| 持续 | 至少 7 天 |
| 记录 | CSV：时间、RTT_p50、RTT_p95、loss%、jitter、TTFB、成功与否 |

## 实验：把「感觉」变成「数据」

一个最小可用的测量函数（Python 标准库，无依赖）：

```python
import subprocess, statistics, platform, time

def ping(host, count=20):
    flag = "-n" if platform.system() == "Windows" else "-c"
    out = subprocess.run(["ping", flag, str(count), host],
                         capture_output=True, text=True).stdout
    # 从输出里提取每次的延迟（Windows 是 "时间=xxms"，Unix 是 "time=x.x ms"）
    import re
    vals = [float(x) for x in re.findall(r"(?:time|时间)[=<]\s*([\d.]+)", out)]
    if not vals:
        return None
    return {
        "n": len(vals),
        "p50": statistics.median(vals),
        "p95": sorted(vals)[int(len(vals) * 0.95) - 1],
        "jitter": statistics.pstdev(vals) if len(vals) > 1 else 0.0,
        "loss": (count - len(vals)) / count * 100,
    }
```

把它扩成完整脚本，跑一周。

> 注意：**不同系统的 ping 输出格式不同**，正则要兼容。这是「跨平台脚本」的第一个坑。
